> **Date :** 2026-05-14
> **Auditeur :** Cowork (Claude)
> **Périmètre :** `planning-lde/` — backend `serve-avancement.py` (1470 l.), dashboard monolithique `AVANCEMENT-PROJETS.html` (6621 l. / 208 Ko), tests `tests_serve.py` (707 l., 82 tests unittest), script one-shot `push_charge_raf.py`, données externes `avancement-dates.json`.

## 1. Synthèse exécutive

V1 est **un outil mature, opérationnel et bien testé** (82 tests unitaires, 5 années d'itération) mais **structurellement contraint par un choix initial** : la persistance dans des blocs sentinelles regex au sein d'un HTML de 6 600 lignes. Ce choix a permis un déploiement rapide en `file://` sans backend, mais il porte aujourd'hui l'essentiel des dettes du projet — fragilité des écritures, illisibilité des diffs git, couplage UI/données, dépendance regex.

**Quatre axes critiques émergent :**

1. **HTML monolithique 208 Ko** comme source de vérité — toute modification met le fichier entier en jeu, l'écriture n'est pas atomique, les diffs git sont inexploitables, et 6 blocs regex distincts portent les données métier.
2. **Absence de garde-fous infrastructure** héritée des phases initiales — pas de `MAX_PAYLOAD`, pas de header CORS, pas d'écriture atomique sur le HTML, pas de backup avant les opérations destructives.
3. **Bibliothèque GSheet lourde** (`google-api-python-client`) avec opérations dispersées dans 30+ fonctions module-level, beaucoup d'appels API individuels (formatage colonne par colonne, validation par cellule, format conditionnel statut par statut).
4. **Trois SPEC concurrentes** (`SPEC-SERVE-AVANCEMENT.md`, `SPEC-PHASE6-TCD.md`, `SPEC-COMPLEMENT-PROJETS.md`) — pas de spec consolidée, le contrat actuel est implicite dans le code.

**Points forts notables :** **82 tests unitaires** réellement exécutables (avec mocks `unittest.mock.patch` sur `_gsheet_service`), bonne séparation Handler / opérations GSheet, helpers `_proj_label`, `_is_lde_project`, `_feat_for_push` propres et testés isolément, gestion correcte du fallback `file://` via `avancement-dates.json`, garde-fou path traversal présent.

## 2. Architecture

### 2.1 Vue d'ensemble

```
AVANCEMENT-PROJETS.html (208 Ko, 6621 lignes)
  ├── UI : structure DOM, CSS, JS (l. 1-264)
  ├── const PROJECTS = [...]              (l. 265-626) — source statique
  ├── const SAVED_DATES = {...}           (l. 628-920) — sentinelles regex
  ├── const SAVED_STATUS = {...}          (l. 924-1915) — idem
  ├── const NEW_FEATURES = [...]          (l. 1919-3136) — idem
  ├── const SAVED_GSHEET_DATA = {...}     (l. 3140-5392) — idem
  ├── const NEW_PROJECTS = [...]          (l. 5396-5487) — idem
  └── JS d'interaction (l. 5488-6621)
       ↓ fetch /api/*
   serve-avancement.py (port 8000, 1470 lignes, mono-fichier)
       ↓ regex sentinelles ↓
   réécriture HTML       Google Sheets (google-api-python-client)
                           ├── Onglet Taches
                           ├── Onglet Liste Projet
                           └── (TCD Projets — phase 6, partiellement implémentée)
   avancement-dates.json (fallback file:// — migration automatique au démarrage)
   avancement-history.jsonl (logs des mutations)
```

### 2.2 Constats positifs

- **Fallback `file://`** — le dashboard est utilisable sans serveur (lecture seule). Les dates sont chargées depuis `avancement-dates.json` au démarrage et migrées dans `SAVED_DATES` au premier lancement (`_migrate_dates_json`, ligne 1368). Bonne propriété de résilience.
- **Helpers de transformation testés isolément** — `_proj_label`, `_is_lde_project`, `_feat_for_push`, `_feat_to_row`, `_row_key`, `_gs_row_to_fields` sont chacun couverts par leur propre classe de test (`TestProjLabel`, `TestRowKey`, `TestFeatToRow`, etc.). Bonne pratique.
- **Séparation Handler / opérations GSheet** — la classe `Handler` (l. 159-682) reste un thin wrapper qui délègue à des fonctions module-level (`_init_gsheet`, `_apply_sync_to_gsheet`, `_apply_pull_from_gsheet`). Pas de logique métier dans les méthodes HTTP.
- **`_log()` centralisé** — chaque mutation passe par `_log()` qui écrit dans `avancement-history.jsonl` avec timestamp. Bonne traçabilité.

### 2.3 Constats à surveiller

**A1. Données dans le HTML — choix structurellement contraignant (P0)**

Les 6 blocs (`PROJECTS`, `SAVED_DATES`, `SAVED_STATUS`, `NEW_FEATURES`, `SAVED_GSHEET_DATA`, `NEW_PROJECTS`) sont **tous** stockés dans un seul fichier `.html` versionné. Conséquences :

- Un diff git sur le HTML produit des centaines de lignes de bruit pour 1 changement métier.
- Toute édition manuelle du HTML (changement CSS, refactor JS) impose de relire tous les blocs sentinelles pour ne rien casser.
- Le fichier fait 208 Ko, soit la taille d'un mini-PDF — l'application charge ces données en synchrone à chaque ouverture (l'utilisateur attend la première peinture).
- Les éditeurs (VS Code, Cursor) sont sensibles à la taille des HTML et certaines opérations (formatage, fold, recherche regex) ralentissent.

V2 a déjà résolu ce point en séparant `data.json` du `DASHBOARD-V2.html` (shell UI pur). Le constat ici est **pour mémoire** — c'est la dette qui a motivé V2.

**A2. Sentinelles regex — fragilité par construction (P0)**

5 regex DOTALL (`_SAVED_DATES_RE`, `_SAVED_STATUS_RE`, `_NEW_FEATURES_RE`, `_SAVED_GSHEET_DATA_RE`, `_NEW_PROJECTS_RE`, lignes 19-39 de `serve-avancement.py`) parsent chacune un bloc JSON entre `// <<XXX_START>>` et `// <<XXX_END>>`. Risques :

- `re.DOTALL` est non-greedy par défaut sur le `.*?` mais reste sensible à la présence d'un commentaire JS qui ressemblerait à un marqueur (`// <<...>>` dans une chaîne par exemple).
- Si JSON.stringify côté serveur produit un format légèrement différent (espaces, échappement Unicode), la regex sur le bloc résultant continue de marcher, mais le diff git est encore plus illisible.
- Une seule sentinelle absente (`if not m: return error`) fait échouer l'endpoint mais corrompt la confiance sur la robustesse.
- La regex est dupliquée dans `tests_serve.py` (lignes 26-41) — source unique cassée si le format change.

**A3. Trois SPEC, pas une seule consolidée (P2)**

- `SPEC-SERVE-AVANCEMENT.md` (22 Ko, 486 l.) — spec du serveur global.
- `SPEC-PHASE6-TCD.md` (17 Ko, 396 l.) — phase 6 spécifique au TCD.
- `SPEC-COMPLEMENT-PROJETS.md` (5 Ko, 83 l.) — complément.

Aucune ne marquée « current » ou « obsolète ». Un nouvel arrivant doit lire les trois pour reconstituer le contrat actuel. V2 résout en une SPEC unique (`SPEC-PLANNING-V2.md`).

**A4. `push_charge_raf.py` — script one-shot oublié (P1)**

Ligne 2 du fichier : `"""One-shot : pousse charge et RAF depuis le HTML vers GSheets colonnes G et H. À supprimer après usage."""`. Le commentaire indique son obsolescence prévue mais il est toujours là. Re-parse le HTML par regex *en dehors* de `serve-avancement.py` — duplication de la logique d'extraction. À supprimer ou à archiver.

**A5. `_PROJECT_FOLDERS` hardcodé + incomplet (P2)**

Lignes 43-50 : 6 projets mappés. Tous les projets actifs du CLAUDE.md racine ne sont pas couverts (Training V7, Examens V7, Brief Équipe, Tests e2e Python, etc.). Le bouton 📁 sera muet pour ces projets. Même constat qu'en V2.

**A6. Endpoints API dispersés sans groupement explicite (P2)**

`Handler.do_POST` (l. 176-200) liste 10 endpoints en `if/elif`. À comparer avec V2 qui a la même structure. Pas vraiment un défaut, mais à 15+ endpoints, le dispatching par routeur (dict ou pattern matching) deviendrait plus lisible.

## 3. Robustesse

### 3.1 Persistance HTML — surface de risque principale

**R1. Écriture HTML non-atomique (P0)**

Toutes les mutations passent par `HTML_FILE.write_text(html, encoding='utf-8')` (lignes 275, 330, 371, 424, 480, 617, 642, 664, 1392). Le fichier fait 208 Ko. Si le process est tué (Ctrl+C, panne, OOM) pendant l'écriture, le HTML peut être tronqué — et c'est **à la fois l'UI et la source de vérité des données** qui sont perdues.

Plus grave qu'en V2 : la corruption affecte aussi le chargement de la page (pas que les données). Et le `_migrate_dates_json` au démarrage (l. 1456 dans `main()`) réécrit potentiellement le HTML — une coupure de courant pendant un démarrage = HTML cassé.

**Reco :** `tmp + os.replace()` pour toutes les écritures HTML. Pattern standard, 15 minutes de travail.

**R2. Pas de backup avant opérations destructives (P0)**

- `_handle_gsheet_init` (l. 532-550) → vide les onglets Taches et Liste Projet (`values().clear()` ligne 1011). Confirmation côté UI via `force=False` qui vérifie les orphans, mais une fois `force=True` envoyé, c'est irrécupérable côté GSheet.
- `_handle_pull_from_gsheet` (l. 588-681) → réécrit `SAVED_GSHEET_DATA`, `NEW_FEATURES`, `SAVED_STATUS` dans le HTML sans backup préalable.

V1 a un mécanisme de préviewing (`/api/pull-from-gsheet/preview`) mais aucune sauvegarde du HTML avant `/api/pull-from-gsheet` (non-preview).

**Reco :** copier `AVANCEMENT-PROJETS.html` → `AVANCEMENT-PROJETS.html.bak` avant chaque pull ou init. Rotation manuelle de 3-5 backups.

**R3. Concurrence push/pull/save sur le HTML (P1)**

Le serveur est mono-thread (`http.server.HTTPServer`), donc deux requêtes ne se chevauchent pas. Mais : pendant un `_apply_pull_from_gsheet` qui peut prendre 10+ secondes (multiples API calls), d'autres requêtes sont **bloquées**, et le HTML est lu/écrit jusqu'à 3 fois dans le même handler (l. 600, 621, 647). Une coupure en cours d'écriture = état incohérent partiel (enrichment écrit mais owner_updates pas encore).

**Reco :** consolider l'écriture HTML en *une seule passe* à la fin de `_handle_pull_from_gsheet` — lire le HTML une fois, faire tous les remplacements regex en mémoire, écrire une fois (atomiquement).

**R4. Pas de `MAX_PAYLOAD` (P0)**

`_read_json_body` (l. 215-217) :

```python
def _read_json_body(self):
    length = int(self.headers.get('Content-Length', 0))
    return json.loads(self.rfile.read(length))
```

Un client malveillant peut envoyer `Content-Length: 10000000000` et bloquer/épuiser le process. Sur `127.0.0.1` la surface est minime, mais V2 a un plafond explicite (`MAX_PAYLOAD = 1_000_000`) — V1 ne devrait pas se contenter de moins.

**Reco :** ajouter `MAX_PAYLOAD = 5_000_000` (le HTML envoyé par `save-features` peut être conséquent) et un check 413 si dépassement.

### 3.2 Gestion d'erreurs et cas limites

**R5. `_handle_*` capturent `Exception` génériquement** (lignes 253, 292, 339, 376, 429, 485, 500, etc.)

Toutes les routes ont `except Exception as e: self._json_error(str(e))` final. Conséquences :
- `KeyError`, `JSONDecodeError`, exceptions Google API : tout devient un `500` indiscernable.
- La stack trace n'est ni loggée ni renvoyée — debug à distance impossible sans accès direct au shell.

**Reco :** logger `traceback.format_exc()` sur stderr en plus de `self._json_error`. Renvoyer des codes plus précis (4xx pour erreurs client, 5xx pour erreurs serveur).

**R6. Aucun handler `OPTIONS` (preflight CORS) (P2)**

Le serveur ne définit pas `do_OPTIONS`. Implicitement, `BaseHTTPRequestHandler` renvoie 501. Comme aucun header `Access-Control-Allow-Origin` n'est jamais posé, **toute requête cross-origin est refusée par le navigateur**. C'est paradoxalement **plus sécurisé que V2** (cf. §6 de l'audit V2 sur CORS `*`), mais ce n'est probablement pas un choix conscient — c'est l'absence d'un feature plutôt qu'une décision défensive.

**R7. `_handle_gsheet_status` renvoie les détails de l'erreur au client** (l. 500-501)

```python
except Exception as e:
    self._json_ok({'connected': False, 'error': str(e)})
```

V2 a le même problème (réf. R6 audit V2) mais V1 va plus loin : envoie `str(e)` au client. Pour un OAuth `invalid_grant`, le client peut voir des fragments de tokens ou IDs dans le message d'erreur. Local-only donc limité, mais à corriger.

**R8. Migration `_migrate_dates_json` au démarrage (l. 1368-1395) sans guard de cohérence**

Lit `avancement-dates.json`, vérifie si `SAVED_DATES` est vide, et si oui, copie. Mais :
- Si `SAVED_DATES` est `{}` parce que l'utilisateur a *intentionnellement* vidé ses dates, la migration les ré-injecte au prochain redémarrage.
- Aucun marqueur « migration faite » — la migration est *toujours* candidate à s'exécuter.

**Reco :** ajouter un fichier `.migration-done` ou une clé `migrated_at` dans `serve-avancement.conf.json`.

**R9. `_apply_pull_from_gsheet` peut perdre des données si certaines sentinelles manquent (l. 588-681)**

Les blocs `SAVED_GSHEET_DATA`, `NEW_FEATURES`, `SAVED_STATUS` sont mis à jour séquentiellement, chacun avec un `if m:` qui silencieusement skip si la sentinelle est absente. Une corruption partielle du HTML (un seul bloc absent) → pull réussit avec ok=true mais une partie des données est perdue. Aucune assertion forte d'invariant.

**Reco :** vérifier la présence des 5 sentinelles **au démarrage du serveur** (`main()`), arrêter avec erreur explicite si l'une manque.

**R10. `_history.jsonl` non borné (P2)** — déjà 12 Ko, va grossir. Même reco que V2 (rotation).

## 4. Maintenabilité

### 4.1 Constats positifs

- **Tests fonctionnels riches** — 82 méthodes `def test_*` dans `tests_serve.py`, organisées par feature (`TestSaveDates`, `TestSaveFeatures`, `TestAddFeature`, `TestHistorique`, etc.). Style unittest classique mais propre, fixture `setUpModule` qui démarre un vrai serveur HTTP sur port 8099.
- **Mocks pour Google API** — `@patch.object(srv, '_gsheet_service')` permet de tester les flux GSheet sans network. C'est *mieux* que V2 (qui skip les tests GSheet).
- **Helpers purs et testés isolément** — `_proj_label`, `_is_lde_project`, `_feat_for_push`, `_feat_to_row`, `_row_key`, `_gs_row_to_fields` ont chacun leurs tests dédiés.
- **Une seule lecture du HTML par requête (la plupart du temps)** — le code charge `html = HTML_FILE.read_text(...)` une fois et travaille en mémoire avant d'écrire.

### 4.2 Dettes structurelles

**M1. `serve-avancement.py` — 1470 lignes, 30+ fonctions module-level (P1)**

Le fichier mélange :
- Handler HTTP (159-682)
- Opérations Google Sheets (684-1363)
- Helpers de mapping (686-720)
- Migration (1366-1395)
- CLI (1398-1466)

Pas de séparation en modules (vs V2 qui sépare api.js / ui.js / app.js côté front, mais a aussi un `serve-v2.py` monolithique côté back — donc équivalent côté Python). Lecture difficile pour qui n'a pas vécu l'évolution.

**Reco :** découper en :
- `serve_avancement/server.py` — Handler + main
- `serve_avancement/html_io.py` — regex sentinelles + lecture/écriture HTML
- `serve_avancement/gsheet_init.py` — `_init_gsheet`, `_build_format_requests`, `_setup_liste_projet`
- `serve_avancement/gsheet_sync.py` — `_apply_sync_to_gsheet`, `_sync_to_gsheet_diff`
- `serve_avancement/gsheet_pull.py` — `_apply_pull_from_gsheet`, etc.
- `serve_avancement/mappers.py` — `_proj_label`, `_feat_to_row`, `_gs_row_to_fields`...

Non urgent (le code marche) mais c'est le pivot pour une éventuelle V3 ou un onboarding.

**M2. Imports inline dans des fonctions (P2)**

`_log` (l. 109) : `from datetime import datetime`
`_feat_to_row` (l. 721) : `from datetime import date as _date`
`_get_gsheet_credentials` (l. 133-135) : 3 imports Google
`_gsheet_service` (l. 154-155) : `from googleapiclient.discovery import build`
`_gs_serial_to_date` (l. 1227) : `from datetime import ...`
`_gs_row_to_new_feature` (l. 1242) : `import hashlib`

Cohérent avec une logique « éviter d'importer Google si on n'utilise pas la GSheet » (lazy loading), mais répartit la lecture des dépendances. Concentrer les imports top-level pour les modules standards (`datetime`, `hashlib`) et garder lazy pour Google.

**M3. Tests : duplication de regex avec le code de prod (P1)**

`tests_serve.py` lignes 26-41 redéfinit exactement les 4 regex sentinelles. Si une regex évolue dans `serve-avancement.py`, il faut penser à les répercuter dans les tests. Source unique cassée.

**Reco :** importer les regex depuis `srv` : `srv._SAVED_DATES_RE` etc. (déjà imposable car `srv = importlib.util.module_from_spec(...)` charge le module).

**M4. `push_charge_raf.py` re-implémente l'extraction depuis le HTML (P1)**

Lignes 17-50 : regex sur `PROJECTS = [...]` faite *à la main* dans le script, indépendamment des regex de `serve-avancement.py`. Logique dupliquée, divergence assurée.

**Reco :** supprimer `push_charge_raf.py` (le commentaire en tête le préconise : « À supprimer après usage »).

**M5. Commentaires sur la dette technique présents dans le code (P2)**

Ligne 1137-1138 de `serve-avancement.py` : « Colonne F (Cible Date) : jamais écrasée avec '' — les features done n'ont pas de target dans le HTML, GSheets fait foi pour cette colonne. »

Ce genre de commentaire signale une asymétrie connue mais non documentée dans la SPEC. À remonter dans `SPEC-SERVE-AVANCEMENT.md`.

### 4.3 Tests

**T1. 82 tests fonctionnels — couverture solide (P0 — constat positif)**

Vraie suite, vrai serveur HTTP en setUpModule, mocks Google API. Bien meilleur point de départ que V2 (qui a moins de tests et skipif sur GSheet).

**T2. Pas de test de corruption du HTML (P1)**

Aucun test ne simule un HTML sans une sentinelle, avec une sentinelle malformée, avec du JSON cassé entre les bornes. Tous les `if not m: return error` sont non couverts.

**T3. Pas de test de concurrence (P2)**

Le serveur est mono-thread, donc pas d'urgence — mais aucun test ne vérifie qu'un push partiellement interrompu (mock `write_text` qui lève après l'avoir partiellement écrit) ne corrompt pas le HTML.

## 5. Performances

### 5.1 Constats positifs

- **Mocks GSheet en test** = pas de latence réseau pour les 82 tests, qui tournent en < 5 secondes.
- **Lecture HTML une fois par handler** pour la plupart des routes.

### 5.2 Constats à surveiller

**P1. Lecture/écriture de 208 Ko à chaque mutation (P1)**

Chaque `save-dates`, `save-features`, `add-feature`, `add-project` lit puis réécrit le HTML entier. À 100 ms de I/O sur un SSD moyen, ce n'est rien. Mais l'opération `_handle_pull_from_gsheet` lit/écrit le HTML **3 fois consécutives** (l. 600, 621, 647). Soit 600 Ko d'I/O par pull. Mineur en absolu, mais inutile.

**Reco :** consolider en une seule lecture-modification-écriture (voir R3).

**P2. Regex DOTALL sur 208 Ko (P2)**

`_SAVED_DATES_RE.search(html)` parcourt potentiellement les 208 Ko avant de trouver la marque. Avec `re.DOTALL` et `.*?`, c'est non-greedy, donc en pratique rapide — mais c'est répété 5 fois par handler GSheet (une par bloc). À l'échelle actuelle, invisible.

**P3. `_init_gsheet` génère 30+ requêtes Google API en cascade (P1)**

Lignes 766-876 (`_build_format_requests`) : pour formater l'onglet Taches, le code génère :
- 1 requête pour le header
- 1 pour le frozen row
- 14 pour les largeurs de colonnes (`_COL_WIDTHS`)
- 2 pour le format date (E, F)
- 2 pour le format numérique (G, H)
- 5 conditional format rules sur le statut
- 5 sur la qualif
- 4 validations (statut, qualif, catégorie, dev)

→ ~30 sous-requêtes dans un seul `batchUpdate`, OK c'est groupé. Mais ensuite (l. 1058) `_setup_liste_projet` fait un *autre* `batchUpdate` + un `values().update`. Et `_init_gsheet` lui-même fait 3 `values().clear()` + 1 `values().update` + 2 `batchUpdate`. Soit ~6 round-trips réseau par init.

V2 avec `gspread` est plus concis : `ws.update()` puis `batch_update` selectif. Différence d'ergonomie de bibliothèque, pas de bug.

**P4. `_apply_sync_to_gsheet` : `batchUpdate` cellule par cellule (P2)**

Lignes 1140-1166 : pour chaque feature à mettre à jour, jusqu'à 5 entrées dans `batch_data` (une par colonne changée). Pour 100 features modifiées → potentiellement 500 entrées dans `batchUpdate` → toujours dans un seul appel mais le payload réseau croît linéairement.

OK pour l'échelle actuelle.

**P5. `google-api-python-client` plus lourd que `gspread`** (P2)

Choisir `gspread` (V2) ou `google-api-python-client` (V1) n'est pas un mauvais choix en soi, mais le second exige plus de boilerplate pour des opérations simples (`values().update().execute()` vs `ws.update(...)`). Volume de code GSheet : V1 a ~800 lignes (l. 684-1395) vs V2 ~500 lignes pour des fonctionnalités équivalentes. C'est un coût de maintenabilité, pas de runtime.

## 6. Sécurité

### 6.1 Constats positifs

- **`Bind('127.0.0.1', port)`** (ligne 1449) — pas accessible depuis le réseau local. ✓
- **Path traversal protégé** dans `_resolve_project_path` (l. 60) — identique à V2. ✓
- **Secrets gitignored** (`client_secret.json`, `token.json`, `avancement-history.jsonl`, `avancement-dates.json`, `serve-avancement.conf.json`, `*.xlsx`, `terminal.txt`, `.claude/`). ✓
- **Pas de header `Access-Control-Allow-Origin: *`** — donc les fetch cross-origin sont *implicitement* refusés par le navigateur (paradoxalement plus sécurisé que V2). ✓ (mais non intentionnel)
- **`shutil.which('open')` check avant subprocess.Popen** (l. 521) — évite un crash silencieux sur Linux. Mieux que V2.

### 6.2 Constats à surveiller

**S1. Pas de `MAX_PAYLOAD` (P0)** — déjà mentionné en R4. DoS facile via Content-Length forgé.

**S2. `_json_error(str(e))` expose les exceptions internes (P1)**

Toutes les routes ont `except Exception as e: self._json_error(str(e))`. Pour un environnement local mono-utilisateur, c'est tolérable, mais c'est une mauvaise habitude qui se reporterait mal si V1 était un jour exposé au réseau.

**S3. `_handle_gsheet_status` renvoie `'error': str(e)` (P1)** — cf. R7.

**S4. `subprocess.Popen(['open', folder])` macOS-only** — mais avec `shutil.which` check (mieux que V2).

**S5. xlsx tracking — vérifié OK**

`.gitignore` contient `*.xlsx` (l. 13). Vérification : `git ls-files | grep xlsx` retourne vide. Les 3 fichiers `.xlsx` dans le répertoire ne sont **pas** dans le repo. ✓

**S6. Logs non-rotés (cf. R10)**

### 6.3 Risques liés au modèle de données

**S7. Sentinelles regex = surface d'injection théorique (P2)**

Un client malveillant pourrait, via `save-features` ou `add-feature`, envoyer un payload contenant la chaîne `// <<SAVED_STATUS_END>>` dans une valeur de champ. Après `json.dumps(..., ensure_ascii=False)`, cette chaîne serait écrite littéralement dans le HTML… brisant les sentinelles. Le prochain parsing échouerait.

En pratique : `json.dumps` n'échappe pas les `/` ni les `<`, donc une chaîne `"// <<SAVED_STATUS_END>>"` passerait telle quelle. Bug latent — non exploité car le serveur est local et LDE n'envoie pas ces chaînes — mais à connaître.

**Reco :** sanitiser ou rejeter les payloads contenant `<<` ou `_START>>` / `_END>>`.

## 7. Recommandations priorisées

### P0 — à traiter rapidement

| ID | Constat | Reco synthétique | Effort estimé |

## 8. Conclusion

V1 est **un projet qui a tenu**, malgré une architecture initiale (HTML monolithique + sentinelles regex) qui aurait dû devenir limitante bien plus tôt. La couverture de tests (82 cas), les helpers purs et testés isolément, et la traçabilité (`avancement-history.jsonl`) sont des points forts qui font qu'on peut **continuer à exploiter V1 en confiance** pendant la transition vers V2.

Les **trois priorités absolues si V1 reste en production** quelques semaines de plus :

1. **`MAX_PAYLOAD`** (15 min) — pas négociable, c'est un trou trivial à boucher.
2. **Écriture HTML atomique** (30 min) — V1 stocke dans le HTML *à la fois* les données et l'UI. Une corruption = double perte.
3. **Backup avant pull/init GSheet** (30 min) — la classe de bugs « j'ai cliqué Pull et j'ai tout perdu » coûte cher à récupérer même avec git (le HTML change tous les jours).

Au-delà : la dette technique de V1 est **réelle mais bornée**. Tout ce qui est listé en P1/P2 a une raison d'être (héritage, choix initial, contrainte `file://`) — V2 résout *structurellement* ces points. **La décision rationnelle est de stabiliser V1 (P0 ci-dessus) puis de basculer sur V2** plutôt que d'investir sur les P1/P2 de V1.
