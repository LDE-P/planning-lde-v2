## 1. Synthèse exécutive

Le projet est **globalement sain, bien documenté et cohérent avec sa SPEC**. La trajectoire V1→V2 a tenu ses promesses : suppression des sentinelles HTML, isolation `data.json` comme source unique, séparation propre HTML / JS / API. Les tests fonctionnels existent et couvrent les cas nominaux des endpoints non-GSheet. La doc (CLAUDE.md, SPEC, TESTS, Améliorations) est exceptionnellement bonne pour un projet de cette taille.

**Trois axes méritent attention prioritaire :**

1. **Robustesse de `data.json`** — écriture non-atomique, pas de verrou, pas de sauvegarde avant opérations destructives (pull GSheet, init GSheet). Un crash pendant `_save_data()` ou une concurrence push/pull peut corrompre la source de vérité.
2. **Couverture des tests GSheet** — les chemins critiques (push, pull Tâches, pull TCD) sont marqués `skipif(GSHEET_AVAILABLE=False)` donc **jamais exécutés en CI**. Toute la logique métier la plus délicate (formules, formats locaux FR, race conditions Semaines→TCD) n'a pas de filet.
3. **Dette UI naissante** — `ui.js` est monolithique (737 lignes) et `renderAll()` recrée tout le DOM à chaque modification. À l'échelle actuelle (~15 SP) c'est invisible, mais la stratégie ne tiendra pas si V2 grossit.

**Aucun risque critique sur la sécurité** dans le périmètre actuel (serveur lié à `127.0.0.1`, secrets gitignored, `MAX_PAYLOAD` en place, sanitisation HTML correcte sur les surfaces principales). Quelques résidus mineurs documentés en §6.

## 2. Architecture

### 2.1 Vue d'ensemble

```
DASHBOARD-V2.html (shell UI pur)
       ↓ <script type="module" src="app.js">
   app.js (entrée, fetch initial, wiring callback)
       ↓
   ui.js (rendu DOM + handlers) ──→ api.js (fetch wrappers /api/*)
                                              ↓
                                       serve-v2.py (port 8001)
                                         ↓        ↓
                                   data.json   gspread → Google Sheets
                                                          (Tâches, Semaines, TCD)
```

### 2.2 Constats positifs

- **Séparation HTML/JS conforme à la SPEC** — aucun JS inline, aucune donnée dans le HTML. Le shell UI est respecté à la lettre.
- **`api.js` est minimal et propre** (77 lignes) — pas de logique métier, juste des wrappers `fetch`.
- **`serve-v2.py` est mono-fichier mais bien structuré** — sections balisées en commentaires (`── Data helpers ──`, `── GSheet ──`, etc.), séparation claire entre helpers, opérations GSheet et handlers HTTP.
- **Endpoints REST cohérents** — verbes HTTP corrects (GET pour lectures, POST pour mutations), payloads JSON, codes HTTP appropriés (400 / 404 / 413 / 500).
- **Modèle Projet → SP → Étape lisible** — la hiérarchie en 3 niveaux tient ses promesses de simplification vs V1.
- **`setFetchStateCallback` (app.js→ui.js)** — découplage propre pour éviter une dépendance circulaire.

### 2.3 Constats à surveiller

**A1. Couplage entre `_PROJECT_FOLDERS` (serve-v2.py:44-52) et `proj.folder` (data.json)**

Deux sources de vérité pour la même information. `_resolve_project_path()` regarde d'abord le mapping statique, puis tombe en fallback sur `data.json`. Conséquences : un projet créé via la GSheet (pull) n'aura pas de `folder` (ligne 553 — initialisé à `''`), donc le bouton 📁 ne fera rien. À l'inverse, ajouter un projet via le dashboard ne renseigne pas `folder` non plus (cf. `_handle_add_project` ligne 1188 : `'folder': payload.get('folder', '')` mais le modal n'envoie pas ce champ).

**A2. SPEC vs CLAUDE.md vs code — divergence sur la colonne `target` GSheet**

- `SPEC-PLANNING-V2.md` §1.3 : « La colonne `Cible Date` de la GSheet est **en lecture seule** (calculée). »
- `CLAUDE.md` projet, tableau de sync : « E | `target` | bidirectionnel »
- `serve-v2.py` ligne 589-590 : `if target: sp['target'] = target` — donc bidirectionnel.

Le code et le CLAUDE.md sont alignés ; la SPEC est stale sur ce point. À retrancher de la SPEC pour éviter qu'un futur Ping-Pong reparte du mauvais pied.

**A3. `_TACHES_HEADERS` (12 colonnes) ne correspond pas à la SPEC §5.1 (12 colonnes A-L mais ordre différent)**

Le code définit : `Projet, Sous-projet, Type, Prio., Cible, Charge, RAF, Titre, Avanc., Commentaire, Semaine, Année`
La SPEC §5.1 a la même structure. **OK** — fausse alerte, mais l'ordre des colonnes K et L (Semaine/Année) dans la doc CLAUDE.md V1 mentionne « K, L | semaine / année » alors que la formule `_f_taches_k` génère bien la colonne K = Semaine. Cohérent.

**A4. `_h_to_j` (serve-v2.py:153) n'est jamais utilisé**

Fonction de conversion heures→jours définie mais jamais appelée — la conversion se fait côté GSheet via `CEILING(...;0,1)`. Soit la fonction sera utilisée dans une feature à venir (auquel cas l'ajouter à un TODO), soit c'est du code mort à supprimer.

**A5. `_DEFAULT_STEPS` (ligne 37) dupliqué inline dans `_gs_pull_taches` (lignes 565-569)**

Quand le pull crée un nouveau sous-projet, il définit ses 4 étapes par défaut en dur au lieu de réutiliser `_DEFAULT_STEPS`. Si LDE modifie un jour les étapes par défaut, il faudra penser aux deux endroits. Petit bug en attente.

## 3. Robustesse

### 3.1 `data.json` — source de vérité fragile

**R1. Écriture non-atomique (P0)**

`_save_data()` (lignes 66-70) fait `DATA_FILE.write_text(...)` directement. Si le process est tué pendant l'écriture (Ctrl+C, panne, OOM), `data.json` peut se retrouver tronqué ou vide. La prochaine lecture lèvera `JSONDecodeError` et `_load_data` la traduit en `ValueError('data.json corrompu (JSON invalide)')` — propagé en 500 — sans backup à restaurer.

**Reco :** écriture atomique via `tmp + os.replace()` (POSIX garantit l'atomicité du rename sur le même filesystem). Pattern standard :

```python
tmp = DATA_FILE.with_suffix('.json.tmp')
tmp.write_text(...)
tmp.replace(DATA_FILE)
```

**R2. Pas de verrou concurrent (P1)**

Le serveur est mono-thread (`http.server.HTTPServer`), donc deux requêtes HTTP ne se chevauchent pas. **Mais** : pull GSheet + push GSheet sont des opérations longues (plusieurs secondes), pendant lesquelles d'autres requêtes (save-subproject venant d'un autre onglet ?) seraient **bloquées**, pas concurrentes. C'est OK aujourd'hui mais fragile si on passe à `ThreadingHTTPServer` un jour. Documenter cette propriété (commentaire en tête de `_save_data`) éviterait une régression silencieuse.

**R3. Pas de backup avant pull GSheet (P0)**

`_gs_pull_taches` et `_gs_pull_tcd` modifient `data.json` directement. Si la GSheet a été corrompue (alias renommé par erreur, RAF supprimés en masse, ligne `- xxx` ajoutée à mauvais escient), le pull les répercute sans filet. La preview existe (`/api/pull-from-gsheet/preview`) mais le bouton "Pull Tâches" du dashboard appelle directement le endpoint non-preview — l'utilisateur n'a pas de garde-fou côté UI.

**Reco :**
- Avant `_gs_pull_taches`/`_gs_pull_tcd`, copier `data.json` → `data.json.bak` (rotation simple, dernier état seulement).
- OU appeler la preview en amont côté UI et afficher la modale `showResults` avant de lancer le pull réel.

**R4. `_gs_init` est destructif sans confirmation (P1)**

Le bouton "Init" du dashboard appelle `/api/gsheet/init` qui supprime les 3 onglets (`del_worksheet`) et les recrée à vide. Aucune modale de confirmation, aucun backup de la GSheet. Un clic accidentel = perte du contenu C (Type) et J (Commentaire) si push n'a pas été fait juste avant.

**Reco :** modale de confirmation côté UI (« Vraiment ? Tu vas perdre les colonnes Type et Commentaire si elles n'ont pas été pullées »).

### 3.2 Gestion d'erreurs et cas limites

**R5. Handlers POST GSheet : `except Exception as e: f'Push GSheet échoué : {e}'`** (lignes 1290, 1314, etc.)

Les détails internes (stack trace, paramètres internes) sont stringifiés et renvoyés au client. Pour un serveur strictement local sur 127.0.0.1, ce n'est pas un risque de fuite, mais ça mélange erreurs techniques (`KeyError`, `ConnectionResetError`) et erreurs métier dans le toast UI — pas idéal pour debug. Au minimum, logger côté serveur (print stderr) en plus du message renvoyé.

**R6. `_handle_gsheet_status` mange tous les exceptions silencieusement** (lignes 947-955)

```python
except Exception:
    self._json_ok({'connected': False})
```

Si le token OAuth est expiré et le refresh échoue, l'UI affiche juste "GSheet : non connecté" sans diagnostic. C'est exactement le cas documenté dans le CLAUDE.md racine (« Workaround authentification »). Renvoyer au moins une raison (`{'connected': False, 'reason': 'token expired'}`) aiderait l'utilisateur à savoir s'il faut relancer le flow OAuth ou si c'est un problème réseau.

**R7. `_gs_init` : nettoyage incomplet en cas d'échec partiel (P2)**

Lignes 254-322 : crée un onglet `__init_tmp__`, supprime les 3 cibles, recrée Tâches, Semaines, TCD. Si `add_worksheet('Semaines')` échoue après la suppression (quota Google API, network), l'onglet temporaire et l'onglet Tâches (recréé) restent, mais ni Semaines ni TCD. Pas de `try/finally` pour nettoyer le temp.

**R8. `_recalc_charges` écrase une valeur saisie manuellement** (ligne 1023)

Si l'utilisateur saisit explicitement `sp.charge = 10` puis modifie une étape, la prochaine sauvegarde recalcule `charge = sum(steps)` (probablement ≠ 10) et écrase. Comportement spec-compliant mais peut surprendre. À documenter dans la SPEC (« la charge sous-projet n'est jamais saisie directement — toujours dérivée des étapes »).

**R9. `_handle_save_subproject` accepte n'importe quel champ via le for-loop** (lignes 1007-1009)

```python
for field in ('status', 'qualif', 'target', 'owner', 'charge', 'raf', 'titre', 'name'):
    if field in payload:
        sp[field] = payload[field]
```

Pas de validation : `target` peut être `"2026-13-99"` (invalide), `charge` peut être `"abc"` (string), `name` peut entrer en collision avec un autre SP du même projet (id reste unique mais l'unicité des noms n'est pas vérifiée). À l'échelle actuelle (LDE seul utilisateur), c'est anecdotique. À documenter comme une dette si V2 s'ouvre à d'autres utilisateurs.

**R10. `_friday_from_week_offset` aux frontières d'année (P2)**

Le code (lignes 158-172) gère le passage d'année (`target_week < 1` ou `> max_week`) mais une semaine ISO 53 → 1 sur une année à 52 semaines peut donner des résultats subtilement faux. Pas de tests aux bornes (52→1, 1→53). Risque : un pull TCD en décembre/janvier peut écrire une `target` du mauvais lundi.

### 3.3 Historique JSONL

**R11. `history.jsonl` non borné (P2)**

Déjà 776 lignes / 90 Ko après peu de temps. Pas de rotation, pas de purge, pas de relecture depuis l'UI. À terme, le fichier grossira à l'infini. Mineur tant que le disque n'est pas saturé, mais à anticiper.

**Reco :** rotation à 10 000 lignes ou 1 Mo, ou ouvrir un endpoint `GET /api/history?since=...` pour relecture (utile pour audit / debug).

## 4. Maintenabilité

### 4.1 Constats positifs

- **Documentation exceptionnelle** — CLAUDE.md projet, SPEC, TESTS, Améliorations : tout est à jour, traçable, daté. Le ratio doc/code est excellent.
- **Conventions de nommage cohérentes** — `_internal_helper`, `Handler._public_method`, `_VALID_STATUSES` constantes, snake_case Python / camelCase JS, respect des conventions du langage.
- **Endpoints documentés au plus près du code** — chaque `_gs_*` fonction a un docstring qui rappelle son contrat et sa source (renvoi à `formules.md`).
- **TESTS-V2.md exhaustif** — 319 lignes, chaque endpoint a ses cas nominaux + erreurs + limites listés AVANT l'implémentation. Très bonne pratique.

### 4.2 Dettes naissantes

**M1. `ui.js` monolithique (737 lignes, P1)**

Toutes les responsabilités UI dans un seul fichier : rendu projet/SP/étape, modales (add SP, add proj, rename alias, confirm, results), inline-edit, status menu, toast, GSheet buttons, init. Aucune frontière de module. Au prochain refactor, ce sera douloureux.

**Reco :** découpage naturel en :

- `ui/render.js` — `renderProject`, `renderSubproject`, `renderStep`, `renderAll`
- `ui/modals.js` — toutes les ouvertures/fermetures de modales
- `ui/status-menu.js` — `openStatusMenu`/`closeStatusMenu`
- `ui/inline-edit.js` — `startInlineEdit`
- `ui/toast.js` — `toast`
- `ui/gsheet-actions.js` — handlers Push/Pull/Init/Format
- `ui/state.js` — `_state`, `_filter`, `_openProjects` + getters/setters

Hors plan d'implémentation : à proposer comme spec dédiée si V2 grossit.

**M2. `renderAll()` force un re-render complet à chaque interaction (P2)**

À chaque clic statut, ajout de SP, suppression : `container.innerHTML = ''` puis reconstruction de toutes les cartes projet, tous les badges, tous les listeners. À ~15 SP c'est ~50 nœuds DOM = invisible. À 200+ SP, le scroll, le focus et les inline-edits ouverts se perdront.

**Reco si V2 grossit :** rendre seulement le nœud impacté (`renderSubproject` retourne déjà un élément isolé — le re-réinsérer à la bonne place suffit).

**M3. Code dupliqué `_DEFAULT_STEPS` (cf. A5)**

Mentionné en architecture, à reclasser ici aussi. Une variable, deux endroits.

**M4. Patterns optimistes incomplets (P2)**

Côté UI, les mutations modifient `_state` AVANT le retour serveur (ex: ligne 242-247, `sp.status = newStatus` avant `saveSubproject().then(...)`). Si le serveur échoue, le toast affiche l'erreur mais `_state` reste sur la nouvelle valeur, et l'UI aussi (le `renderAll()` dans `.then()` n'est jamais appelé). Divergence silencieuse entre vue et serveur.

**Reco :** soit pessimiste (attendre la réponse avant d'appliquer), soit optimiste avec rollback dans `.catch()`. Le mix actuel est piégeant.

**M5. Pas de typage** (P2)

Backend : aucun type hint sur les retours de `_gs_push`, `_gs_pull_*` (à part `dict` générique). Frontend : pas de JSDoc sur les payloads attendus. Pour un projet de cette taille c'est tolérable, mais ajouter des types légers (TypedDict côté Python, JSDoc côté JS) ferait gagner du temps en debug.

### 4.3 Tests

**T1. Tests GSheet skippés par défaut (P0)**

`tests-e2e-python/planning-lde/test_gsheet.py` : `GSHEET_AVAILABLE = False` (flag manuel). Aucun test GSheet ne tourne donc en automatique. Or c'est la zone la plus risquée du code (formules locales FR, race conditions Semaines↔TCD, ordre des `batch_clear`/`batch_update`, bug "Impossible d'analyser 0.9" déjà corrigé une fois dans Ameliorations.md).

**Reco :** ajouter des tests **mockés** qui ne nécessitent pas de credentials. Pattern :

```python
@patch('serve_v2.gspread.authorize')
def test_push_preserves_col_c_and_j(mock_auth):
    fake_ws = MagicMock()
    fake_ws.batch_clear.return_value = None
    ...
    serve_v2._gs_push('fake_sid')
    # Assertion : batch_clear appelé avec ['A2:B1000', 'D2:I1000', 'K2:L1000']
    #             jamais avec 'C2:C1000' ni 'J2:J1000'
    fake_ws.batch_clear.assert_called_once_with(['A2:B1000', 'D2:I1000', 'K2:L1000'])
```

Au moins un test mocké par endpoint GSheet (init, push, pull-taches, pull-tcd, format) couvrirait l'essentiel sans appels réseau.

**T2. Pas de test pour `_recalc_charges` (P2)**

La fonction est testée indirectement via `save-subproject`, mais les cas limites (étape `na` exclue, étape sans `charge`, étape avec `charge=null`) ne sont pas couverts isolément. Test unitaire pur Python (sans HTTP) en complément.

**T3. Pas de test sur `_friday_from_week_offset` aux bornes d'année** (cf. R10).

**T4. Pas de test pour la corruption de `data.json`** (T2 dans TESTS-V2.md mais pas dans le code)

Le scénario « `data.json` JSON invalide » est listé dans TESTS-V2.md mais je ne le vois pas dans `test_state.py`. À vérifier.

## 5. Performances

### 5.1 Constats positifs

- **`data.json` reste petit** (~18 Ko pour 15 SP) — pas d'impact perceptible.
- **Mono-thread `HTTPServer`** — pas d'overhead de synchronisation.
- **GSheet : `batch_update` / `batch_clear`** — déjà groupés (lignes 421-428), pas de boucle de cellule individuelle.
- **Frontend : `<script type="module">`** — chargement parallèle des imports JS.

### 5.2 Constats à surveiller

**P1. `renderAll()` recrée tout le DOM** (déjà évoqué en M2). À l'échelle actuelle, non bloquant.

**P2. `_find_sp` est O(projets × sous_projets) par ligne pullée**

Pour 1000 lignes GSheet et 100 SP, ça ferait 100 000 itérations — négligeable en Python mais inutile. Construire un index `dict[(alias_lower, sp_name_lower)] → (proj, sp)` en début de `_gs_pull_taches` réduirait à O(1) par ligne.

**P3. `_get_gspread_client()` recrée la connexion à chaque endpoint** (lignes 98-119, appelée par chacun des 7 handlers GSheet)

À chaque appel, lecture de `token.json`, vérification expiration, possible refresh. Plus quelques secondes de latence si refresh nécessaire. Pour des sessions intensives (push, puis pull TCD juste après), cache mémoire dans le process serait utile :

```python
_GS_CLIENT = None
def _get_gspread_client():
    global _GS_CLIENT
    if _GS_CLIENT is None or not _gs_token_valid():
        _GS_CLIENT = ...
    return _GS_CLIENT
```

**P4. Push : double écriture sur `Semaines` et `TCD Projets` headers** (lignes 416-417)

`ws_s.update('A1:G1', [dyn_headers])` puis `ws_tcd.update('A1:G1', [dyn_headers])` — deux appels API. Pourrait être groupé en un `spreadsheet.values_batch_update()`. Gain : 1 appel API par push.

**P5. Pas de cache HTTP côté client**

`GET /api/state` est appelé sur chaque chargement (et après chaque pull). Pas de `ETag`, pas de `Cache-Control`. Pas un problème en local sans réseau, mais l'absence d'invalidation explicite côté client signifie qu'un onglet ouvert resté longtemps ne verra jamais les modifications faites depuis un autre onglet ou depuis la GSheet (sauf reload).

## 6. Sécurité

Le serveur est lié à `127.0.0.1:8001` — la surface d'attaque externe est nulle dans un usage normal. Les remarques ci-dessous concernent les bordures du modèle de menace.

### 6.1 Constats positifs

- **`Bind('127.0.0.1', port)`** (ligne 1353) — pas accessible depuis le réseau local. ✓
- **`MAX_PAYLOAD = 1_000_000`** appliqué via `_read_json_body` et `_drain_body` — bonne pratique anti-DoS. ✓
- **Secrets gitignored** (`client_secret.json`, `token.json`, `data.json`, `terminal.txt`) — vérifié dans `.gitignore`. ✓
- **Path traversal protégé** dans `_resolve_project_path` (lignes 811-812) — `if root != target and root not in target.parents: return None`. ✓
- **HTML escaping** dans `ui.js` via `esc()` pour les champs injectés en `innerHTML` (lignes 96-104). ✓

### 6.2 Constats à surveiller

**S1. CORS `*` permissif sur localhost** (lignes 829, 901, 921, 930) — P2

`Access-Control-Allow-Origin: *` est posé sur tous les endpoints. Implications :
- Une page web malveillante ouverte dans le même navigateur que LDE peut faire un `fetch('http://localhost:8001/api/save-subproject', {...})` et modifier `data.json` sans avoir besoin de la même origine. C'est un vecteur connu pour les serveurs dev locaux.
- Mitigation simple : remplacer `*` par `http://localhost:8001` (origine self) — la plupart des fetch cross-origin se feront refuser, et la page servie par le même serveur fonctionnera toujours.
- Mitigation forte : ajouter un secret/token dans `serve-v2.conf.json` et l'exiger en header `X-Auth-Token` sur les POST (cohérent avec la Règle 4 du CLAUDE.md racine — « toujours s'appuyer sur l'infrastructure existante » : check si V1 le fait déjà).

**S2. `subprocess.Popen(['open', folder])` (ligne 1231) — P2**

Macos-only. Si LDE bascule un jour sur Linux/WSL, ça crashera. Anecdotique mais à noter pour la portabilité.

Aucun risque d'injection : `folder` est validé en amont par `_resolve_project_path` (path traversal protégé).

**S3. `_handle_save_subproject` accepte des champs arbitraires sans whitelist stricte** (cf. R9) — P2

Le for-loop ligne 1007 ne traite que 8 champs nommés, donc des champs surprises (`__proto__`, `constructor`) sont ignorés silencieusement. Pas de prototype pollution en Python — risque résiduel faible. Mais une validation explicite des types (`isinstance(payload['charge'], (int, float))`) éviterait d'écrire des strings dans des floats.

**S4. Token OAuth en clair dans `token.json` (lignes 106-118)** — P2

Standard pour le pattern `InstalledAppFlow`. Mitigation envisageable : chiffrement via `keychain` macOS (`security` CLI), mais hors périmètre raisonnable pour un outil personnel.

**S5. Pas de rate-limiting sur les endpoints** — P2

Un script malveillant qui exploiterait S1 pourrait faire 100 `POST /api/add-subproject` par seconde et remplir `data.json`. À nouveau, hypothèse de menace très basse pour un outil local mono-utilisateur. Mention pour mémoire.
